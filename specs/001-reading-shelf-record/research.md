## R-001: ISBN からの書誌情報取得元

**Decision**: openBD を第一経路、国立国会図書館サーチ（NDL サーチ）を第二経路とする二段構え。**利用者の承認済み（2026-08-30）**。

**Rationale**:

- openBD は API キー不要、1件あたりの応答が高速、ISBN のカンマ区切りによる一括取得に対応しており、近年刊行のコミックに対するカバレッジが高い。個室内で1冊ずつ記録する本アプリの主経路として応答速度が有利。
- NDL サーチは納本制度に基づくため網羅性が高く、openBD が弱い旧刊（バーコード黎明期〜2007年以前）を補える。加えて **API 側が 10 桁 / 13 桁 ISBN の双方に変換して完全一致検索を行う**ため、10 桁 ISBN（要求定義書 10.）に対する保険になる。
- 利用条件が個人利用に明確に適合するのは NDL サーチ側（個人・非営利で利益を得ない場合は利用申請不要）。openBD は「本の販促・紹介目的に限り使用」「データの任意改変は禁止」と定めており、FR-006（利用者が書誌情報を確認・修正して確定する）との整合に注意が必要（後述の Risk 参照）。

**エンドポイント（実装時に一次情報で再確認すること）**:

| 経路 | エンドポイント | 形式 | 認証 |
| --- | --- | --- | --- |
| openBD | `https://api.openbd.jp/v1/get?isbn=<ISBN13>` （カンマ区切りで複数可） | JSON | 不要 |
| NDL サーチ | `https://ndlsearch.ndl.go.jp/api/sru?operation=searchRetrieve&query=isbn=<ISBN>` | XML (SRU) | 不要 |

**Alternatives considered**:

| 案 | 棄却理由 |
| --- | --- |
| openBD 単独 | 旧刊で取得できず、手入力（FR-007）へ落ちる頻度が上がる。本アプリは漫画喫茶の既刊を読む用途であり、旧刊の比率が無視できない |
| NDL サーチ単独 | 網羅性と利用条件は最良だが、応答が openBD より遅く、SC-001（記録完了30秒以内）に対する余裕が減る。主経路には openBD を置き、NDL は補完に回す |
| 楽天ブックス書籍検索 API | アプリ ID の登録とアプリ内でのキー保管が必要になる。個人利用アプリでキーを配布物に埋め込む形は避けたい |
| Google Books API | 日本のコミックに対するカバレッジと巻数表記が不安定。日次クォータの制約もある |
| Amazon PA-API | アソシエイト審査が前提であり、個人の読書記録アプリの用途に適さない |

**Risks / 留意点**:

- **巻数は独立した項目として保証されない**。openBD（JPRO-onix 準拠）でも巻数がタイトル文字列に含まれるだけの場合がある。R-002 のタイトル解析と、FR-006 の利用者による確認・修正を前提とする。
- **openBD の「データの任意改変は禁止」**は再配布・二次公開を想定した条項と解されるが、本アプリは端末内に閉じ（原則V）、修正内容を外部へ配布しない。この解釈を plan の Constitution Check に記録し、疑義が生じた場合は NDL サーチ単独へ切り替えられるよう、取得経路は R-003 のインターフェースで抽象化する。
- 両経路とも通信を要するため、圏外・電波不良の個室（要求定義書 3.3）では取得できない。**取得失敗は例外ではなく通常経路**として扱い、手入力（FR-007）へ即座に落とす。タイムアウトは 3 秒とし、待たせない。

## R-002: 作品（シリーズ）の同定と巻数の抽出

**Decision**: オンデバイス AI（ML Kit GenAI Prompt API / Gemini Nano）を第一経路、正規表現を第二経路とする連鎖でタイトルから作品名と巻数を読み取り、作品名を正規化した「照合キー」で既存の作品に突合する。抽出結果と突合結果は確認画面に初期値として提示し、利用者が修正・分離できる（FR-027, FR-028）。

**更新（2026-09-04, Issue #4）**: 当初は正規表現のみで巻数を抽出していたが、続巻が別作品として登録される不具合が実機で発覚した（[issue #4](https://github.com/LongbowXXX/reading-tracker/issues/4)）。着手前に実データを収集して原因を測定した（openBD 1,535 件 / NDL 230 件）。

issue 本文の推定「レーベル名の括弧付き接尾辞がタイトル末尾に付く」は openBD では確認できず、レーベル名は `summary.series` という別項目で返っていた。実際の原因は3つだった。

1. **末尾の区切り記号で照合キーが割れる**。コミック 1,129 件中 19 シリーズが分裂していた。openBD の `チェンソーマン 5` と NDL の `チェンソーマン. 5` は同じ本であり、**取得経路が違うだけで別作品になっていた**
2. **巻数表記の語彙不足**（`巻94` / `巻ノ9` / `巻之3` / `vol.8` / `その1` / `#2`）。抽出率 83.3%
3. **区切りの無い数字は正規表現では原理的に判別できない**。`拳児2` は2巻だが `ゴルゴ13` `キャプテン2` は作品名の一部であり、区別には世界知識が要る

1 と 2 は照合キーの正規化と巻数語彙の強化で解消した（末尾記号による分裂 19→0、抽出率 83.3%→88.7%）。3 に対応するためオンデバイス AI を第一経路として導入する方針を採用した（2026-09-04 承認）。

**AI 経路の制約**（[ML Kit GenAI](https://developers.google.com/ml-kit/genai) の公式ドキュメントで確認）:

- **対応端末が限られる**。Pixel 9 以降、Galaxy S26、Z Fold7 など。**Galaxy S25 は Prompt API の対応表に含まれない**（機能別 API の表には含まれる）。非対応端末では `FeatureStatus.UNAVAILABLE` が返るため、**規則ベースの経路を必ず残す**
- **日本語対応の記載が公式ドキュメントに無い**。要約 API・校正 API には対応言語の明記があるが Prompt API には無い。このためプロンプトの指示文は英語で書き、例と入出力を日本語とした
- レイテンシは Pixel 9 の実測で 0.8〜2.1 秒（Google 掲載値）。1経路あたり 2.5 秒で打ち切り、規則ベースへ落とす（原則VI）
- beta（`1.0.0-beta4`）であり、後方互換性を壊す変更がありうる
- 推論は端末内で完結し入出力はネットワークへ出ない（原則V）。ただし ML Kit は API の利用状況メトリクスを Google へ送る（ML Kit 利用規約 Privacy）

**推論の揺れへの対処**: 推論結果が揺れると照合キーが変わり、Issue #4 そのものを再発させる。温度 0・シード固定に加え、**元のタイトルから文字を削っただけかを検証して翻訳・創作を捨て**、結果をキャッシュする。プロンプトの組み立て・応答の解釈・経路の連鎖・照合キーの生成はすべて `:domain` の純粋関数とし、ユニットテストで固定した。推論そのものは実機でしか検証できない（原則IV）。

**Rationale**（当初 正規表現のみを採用した際の判断根拠）:

- 巻ごとに ISBN が異なるため、ISBN だけではシリーズを同定できない（要求定義書 10.）。
- 巻数表記は「◯◯ 12」「◯◯（12）」「◯◯ 第12巻」「◯◯ 12巻」など出版社ごとに揺れる。完全な自動判定は不可能であり、目指さない（spec の Assumptions に明記済み）。
- 誤照合のコストは低い（確認画面で分離できる）一方、毎回作品を選ばせるコストは全記録に掛かる。原則VI（最小手数）から自動照合を既定とする。

**照合キーの正規化規則**（ドメイン層の純粋関数 `buildMatchKey()` として実装し、ユニットテストで固定する）。**2026-09-04 に実データの測定結果へ合わせて改めた**:

1. 全角の英数字・記号・空白を半角へ寄せる
2. 並列書名（`ブーツレグ = BooTsLeG` の `= ` 以降）を落とす。AI 経路は落とした作品名を返し規則ベースは残すため、**照合キー側で吸収しないと経路の違いだけで別作品になる**
3. 空白（半角・全角）を除去する
4. 末尾の巻数表記を除去する
5. 末尾の区切り記号（`.` `。` `,` `、` `:` `;` `=` `/` `-` `ー` `―` `‐` `・`）を落とす。openBD と NDL で付いたり付かなかったりする。`!` `?` `)` は作品名の一部として現れる（`よつばと！` `怪物(けもの)事変`）ため落とさない
6. 大文字小文字を揃える（`act-age` と `Act-Age`）
7. 出版社名・レーベル名は照合キーに含めない（同一作品が別レーベルで再刊される場合があるため）

半角カタカナの全角化は行わない。当初の規則には含めていたが、openBD・NDL のいずれも半角カタカナを返さないため実装しておらず、**規則を実装に合わせて外した**。濁点・半濁点の合成を伴うため「1文字を1文字へ写す」前提が崩れ、巻数表記の抽出位置の計算に影響する点も理由である。

**Alternatives considered**:

| 案 | 棄却理由 |
| --- | --- |
| 記録のたびに利用者が既存作品を選ぶ | 誤照合は起きないが、1冊ごとに操作が1ステップ増える。原則VI に反する |
| 常に新規作成し後から統合する | 統合機能が別途必要になり、今回スコープ外の機能を呼び込む |
| ISBN の出版社記号＋書名記号で判定 | ISBN の内部構造はシリーズの同一性を保証しない |
| NDL の `dc:title` / `dcndl:volume`（構造化された作品名と巻数）を使う | **2026-09-04 の測定では有力だった**（作品名 100% / 巻数 93%、新刊も 100% カバー）。ただし openBD が第一経路であるため経路の入れ替えを伴い、Issue #4 では AI 経路を採る判断をした。AI 経路が期待どおり動かない場合の代替として残す |

## R-003: バーコード読み取りの実装方式

**Decision**: CameraX + ML Kit（バンドル版 `com.google.mlkit:barcode-scanning`）の自前実装を用いる。読み取り部分は `BarcodeScanner` インターフェースで抽象化する。

**更新（2026-09-01, Issue #1）**: 当初は Google Code Scanner（`play-services-code-scanner`）を初期実装として採用したが、`startScan()` 1回につき1件返して終了する仕様のため、書籍バーコード下段（`192` 始まりの日本図書コード）を読み捨てて読み取りを継続できなかった。契約が定めた対象シンボルの規定を満たせず、ここで想定していた差し替えを実施した。インターフェース境界を先に引いていたため、差し替えは `RecordScreen` のスキャナ生成1行に収まり、UI とドメインへ波及しなかった。

**Rationale**（当初 Google Code Scanner を採用した際の判断根拠）:

- スキャン用 UI ごと提供されるため実装量が小さく、動作検証を早く始められる（マスタープロンプトの指定どおり）。
- 暗所でのトーチ制御など細かい調整ができないため、実機で読み取り精度に問題が出た場合は CameraX + ML Kit の自前実装へ切り替える。切り替えがドメイン層・UI 層へ波及しないよう、インターフェース境界を先に引く。
- Google Play 開発者サービス経由でモジュールが配信されるため、初回利用時にダウンロードが発生しうる。通信できない状態で初回スキャンを行う場合に失敗する可能性があり、**手入力への切り替え（FR-003）が同格の経路であることが実装上も必要**（当初はオフラインの個室を想定した記述だったが、通信は店舗の Wi-Fi を前提とする方針へ改めた。2026-09-05、旧 SC-006 の削除）。

**実機検証が必要な項目（原則IV）**:

- 個室の照明環境（暗所）での読み取り可否
- 棚番号シールがバーコードを覆う頻度（要求定義書 9. 未確定事項）
- 片手保持での読み取り成功率と、読み取り→手入力の切り替え操作の実用性

**Alternatives considered**:

| 案 | 棄却理由 |
| --- | --- |
| 最初から CameraX + ML Kit の自前実装 | トーチ制御やフォーカス調整まで作り込めるが、初期の実装量が大きく、動作検証の開始が遅れる |
| ZXing 系ライブラリ | ML Kit と比べて読み取り精度・保守性で劣る |

## R-004: モジュール構成とアーキテクチャ

**Decision**: Gradle マルチモジュール構成とし、`:domain` を Android 非依存の純 Kotlin モジュール（`kotlin("jvm")`）として分離する。`:data` を Android ライブラリ（Room・書誌取得）、`:app` を Compose UI とする。依存方向は `:app → :data → :domain`、および `:app → :domain`。

**Rationale**:

- 原則III（NON-NEGOTIABLE）が求める「Android 非依存」を、パッケージ分割ではなくビルド構成で強制できる。`:domain` に Android 依存を書くとコンパイルが通らないため、原則違反が実装時に自動検出される。
- `:domain` は JVM モジュールのため、エミュレータなしで高速にテストできる。棚番号の継承ロジックをテストで固定する（原則III）際の反復速度が上がる。

**Alternatives considered**:

| 案 | 棄却理由 |
| --- | --- |
| 単一モジュールでパッケージのみ分割 | 実装量は小さいが、Android 依存の混入をレビューでしか防げない。原則III の担保として弱い |
| 機能ごとのモジュール分割（feature-record / feature-visit など） | 今回の画面数は5前後であり、分割の管理コストが利得を上回る。将来スコープが広がった段階で再検討する |

## R-005: 依存ライブラリと DI

**Decision**:

| 用途 | 選定 | 備考 |
| --- | --- | --- |
| UI | Jetpack Compose（BOM で版を揃える） | 決定済み |
| ローカル DB | Room | 決定済み。KSP でコード生成 |
| 非同期 | Kotlin Coroutines / Flow | 決定済み |
| バーコード | CameraX + ML Kit（バンドル版 `com.google.mlkit:barcode-scanning`） | R-003 |
| HTTP | OkHttp | Retrofit を使わず、2経路の差異を `BibliographySource` 実装内に閉じる |
| JSON | kotlinx.serialization | openBD 用 |
| XML | Android 標準の `XmlPullParser` | NDL SRU 用。追加依存を増やさない |
| DI | Hilt | 画面数が少ないため手動 DI でも足りるが、`BibliographySource` と `BarcodeScanner` の差し替え（R-001, R-003）をテストで行う際に有利 |
| 依存管理 | Gradle バージョンカタログ（`gradle/libs.versions.toml`） | 決定済み |

**Rationale**: 差し替えを前提とする箇所（書誌取得・バーコード読み取り）が2箇所あり、いずれもインターフェース境界を持つ。DI コンテナがあるとテスト時の差し替えが宣言的に書ける。

**Alternatives considered**: 手動 DI（コンストラクタ注入のみ）は依存が増えないが、`:app` の生成コードが増えるにつれ配線が煩雑になる。Koin は実行時解決のため、配線ミスがコンパイル時に検出できない。

## R-006: テスト方針

**Decision**:

| 対象 | 方式 | 実行コマンド |
| --- | --- | --- |
| `:domain`（棚番号の継承、状態遷移、次巻判定、ISBN 検証、タイトル正規化） | JUnit 5（純 JVM） | `./gradlew :domain:test` |
| `:data`（Room の DAO、制約違反、マイグレーション） | Robolectric ないし instrumented test | `./gradlew :data:test` / `:data:connectedAndroidTest` |
| `:app`（Compose UI） | 今回は自動テストの対象外。実機での手動確認とする | — |

**Rationale**: 原則III はドメイン層のユニットテストを必須とする。UI の自動テストは今回のスコープでは費用対効果が低く、原則IV が求める実機確認と重複する。

**必ず網羅するテストケース（原則III）**:

1. 棚番号が直前の巻から継承されること
2. 巻単位で棚番号を変更した場合、それ以降の巻に新しい番号が継承されること
3. 作品単位の一括更新が、他店舗の記録に影響しないこと（A-9 はスコープ外だが、**店舗独立性の検証としてドメイン関数レベルで実施する**。UI は作らない）

3 について補足する。憲法 原則III は「作品単位の一括更新が他店舗の記録に影響しないこと」のテストを要求する一方、A-9（一括更新）は今回スコープ外である。今回はドメイン層に一括更新の純粋関数を置き、その戻り値が他店舗の記録を含まないことをテストで固定する。UI からの導線は作らない。これによりスコープを広げずに原則III を満たす。

## R-007: パッケージ名と最小 SDK

**Decision**:

- `applicationId` / ルートパッケージ: `io.github.longbowxxx.readingtracker`
- `minSdk` = 26（Android 8.0）、`compileSdk` / `targetSdk` = 36
- JVM ターゲット: 17

**Rationale**: minSdk 26 は利用者が決定済み。26 以上であれば `java.time` が core library desugaring なしで利用でき、記録日時の扱いが素直になる。パッケージ名は GitHub アカウント由来の逆ドメインとし、実在ドメインの占有を避けた。ストア公開の予定はないが、変更が必要な場合は実装着手前であれば低コストで差し替えられる。

## R-008: オンデバイス AI の可用性判定と起動ゲート

**Decision**: オンデバイス AI の利用可否を `:domain` のポート `AiAvailability` として切り出し、ML Kit GenAI の `checkStatus()` が返す 4 状態を `AVAILABLE` / `PREPARING` / `UNSUPPORTED` の 3 値へ写像する。判定は**起動のたびに**実行し、結果をアプリ側で保持しない。`PREPARING` のときは「準備が必要である旨」と「ダウンロードを開始」の導線を出すにとどめ、**取得の開始は利用者の明示的な操作を起点とする（アプリが自動で開始してはならない）**。開始の操作を受けてから `download()` が返す Flow を購読して準備の完了・失敗を検知し、完了したら追加操作なく本体へ進める。**回線種別（Wi-Fi かモバイルか）の判定は行わず**、開始の判断は利用者に委ねる。起動ゲートはアプリ全体に掛け、AI を使わない画面も含めて `AVAILABLE` になるまで通さない（[issue #9](https://github.com/LongbowXXX/reading-tracker/issues/9)。**利用者の承認済み、2026-09-05**）。

| ML Kit `FeatureStatus` | 写像先 | 意味 |
| --- | --- | --- |
| `AVAILABLE` | `AVAILABLE` | 推論できる。ゲートを外す |
| `DOWNLOADABLE` | `PREPARING` | 対応端末だがモデルが未取得。取得を促せる |
| `DOWNLOADING` | `PREPARING` | 取得中。完了を待てばよい |
| `UNAVAILABLE` / その他 / 判定時の例外 | `UNSUPPORTED` | サポート対象外として扱う |

**Rationale**:

- FR-034 が「非対応」と「準備中」を区別して提示することを求める。対応端末であってもモデル未取得（`DOWNLOADABLE` / `DOWNLOADING`）は初回起動で高い確率で起こるため、これを非対応として見せると**対応端末を非対応と誤って伝える**ことになる。3 値への写像は、この区別を保ちながら画面側の分岐を最小に保つための最小の粒度である。
- 判定 API は端末側の AI 基盤（AICore）へ接続するため例外を投げうる。「判定できなかった」を独立した状態として増やすと画面と分岐が1つ増える一方、利用者に取れる行動（再試行するか、対応端末を使う）は非対応と変わらない。FR-033 が両者を同じ扱いと定めているため、**例外は `UNSUPPORTED` へ畳み込み、文言だけを画面側で分ける**。
- 端末側の AI 基盤は更新で状態が変わりうる。判定結果をキャッシュすると「更新したのに非対応のまま」という状態が残るため、起動のたびに判定する（FR-032）。
- 準備の完了検知に Flow を用いるのは、取得の進捗が不定であり、完了・失敗のいずれも待ち受ける必要があるため。完了時にそのまま本体へ進めることで SC-009 の「追加操作なし」を満たす。
- **取得を自動で開始しないのは、起動が店舗外でも起こるためである。** 通勤中や自宅で開いた場合、従量課金のモバイル回線で大容量のモデル取得が黙って始まりうる。利用者が意図しない通信量の発生は、記録が1タップ増えることよりも損害が大きい。ゲートは「準備が必要である」ことを伝えるところまでを担い、開始の判断は利用者に委ねる。
- **回線種別の判定は採らない。** 接続状態の参照は権限と実装（`ConnectivityManager` の監視と状態変化への追従）を増やすうえ、テザリングや従量課金の Wi-Fi を判別しきれず、結局は判断を誤る。判定を持たない代わりに、開始を明示操作にすることで同じ目的（意図しない大容量取得を防ぐ）を満たす。

**Alternatives considered**:

| 案 | 棄却理由 |
| --- | --- |
| 警告を出したうえで続行させる | 実装は最も軽いが、**AI 前提で機能を足していく方針**（spec の Assumptions）と両立しない。AI が効かないまま静かに劣化した結果を利用者が正しいものとして受け取る |
| `AVAILABLE` 以外を一律にブロックする | 分岐は1つで済むが、モデル未取得の初回起動が非対応の警告として見える。対応端末を非対応と誤って伝えることになり FR-034 に反する |
| 現状のまま（`GenAiTitleAnalyzer` 内部で黙って規則ベースへフォールバック） | どの端末でも記録は完了するが、**AI が効いていないことが利用者に一切見えない**。Issue #9 が問題とした状態そのもの |
| 検知と同時に自動で取得を開始する | 操作は最も少ないが、起動は店舗外でも起こるため、**従量課金のモバイル回線で大容量の取得が黙って始まりうる**。利用者が止める機会を持てない |
| Wi-Fi 接続時のみ自動開始する | 回線種別の判定に権限と実装を要し、テザリングや従量課金の Wi-Fi を判別できない。**自動化しきれない判断を自動化する**ことになり、誤ったときの損害は前案と変わらない |

**Risks / 留意点**:

- **対応端末が限られる**（Pixel 9 以降、Galaxy S26、Z Fold7 など。Galaxy S25 は Prompt API の対応表に含まれない。R-002）。ブロックする以上、非対応端末では起動直後に警告が出て何もできない。これは方針として受け入れた結果である（spec の Assumptions）。
- **初回のモデル取得に時間と通信量を要する。** 店舗の Wi-Fi が利用できることを前提とする（旧 SC-006 は 2026-09-05 に削除済み）。取得に失敗した場合は再試行の手段を出す（FR-034）。
- ML Kit GenAI は beta（`1.0.0-beta4`）であり、`FeatureStatus` の値や `download()` の戻り値が変わりうる。**写像を `:domain` の純粋なロジックへ、ML Kit への依存を `:data` の `GenAiAvailability` へ閉じる**ことで、API 変更の影響範囲を実装1箇所に留める。
- 開発ビルドの回避手段（FR-035）により、配布ビルドと開発ビルドで起動時の振る舞いが異なる。plan.md の Complexity Tracking に記録した。
