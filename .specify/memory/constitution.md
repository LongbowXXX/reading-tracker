# 漫画喫茶 読書記録アプリ Constitution

## Core Principles

### I. 要求定義書を唯一の正とする

`docs/requirements.md` の記載を唯一の正とする。仕様・設計・実装のあらゆる判断は、この文書に
立ち返って行わなければならない（MUST）。

- 文書に記載のない機能を推測で追加してはならない（MUST NOT）。
- 追加・変更が必要と判断した場合は、実装せずに**提案として提示**し、承認を得てから
  `docs/requirements.md` を改訂する（MUST）。
- 要求定義書と本憲法・指示が矛盾する場合は、実装を止めて矛盾点を報告する（MUST）。
- 要求定義書だけでは決まらない点は、勝手に決めず `[NEEDS CLARIFICATION]` として明示する（MUST）。

**根拠**: 個人利用アプリでは「あると便利そう」な機能が際限なく増え、入力手数の増加
（原則VI）とスコープ破綻を招く。正の所在を1箇所に固定することで、判断のブレを防ぐ。

### II. 既存アプリのデータモデルを持ち込まない

本アプリは漫画喫茶で「買わずに読む」ことを前提とする。一般的な漫画管理アプリが前提とする
「購入・所蔵」モデルを持ち込んではならない（MUST NOT）。

- 「購入済み」「所有」「蔵書」「未購入」およびこれらに相当する概念を、ドメインモデル・
  DBスキーマ・UI文言・変数名のいずれにも導入してはならない（MUST NOT）。
- 巻に対して記録する読書状態は「読了」「中断」の2つのみとする（MUST）。
- 「離脱」は作品単位の状態として保持し、来店時の一覧から除外する（MUST）。
- 巻内の読了位置（ページ・話数）は記録しない。必要な補足はメモに委ねる（MUST NOT / MUST）。

**根拠**: 要求定義書「1. 背景と目的」および「8. スコープ外」が明示するとおり、購入・所有管理は
本アプリの解くべき課題ではない。データモデルに一度混入すると、後からの除去は影響範囲が大きい。

### III. ドメインロジックを Android 非依存に分離する（NON-NEGOTIABLE）

以下のロジックは、Android フレームワークに依存しない純粋な Kotlin として実装する（MUST）。

- 棚番号の継承ルール
- 読書状態の遷移
- 次に読むべき巻の判定
- ISBN の妥当性検証（チェックディジット）および 10桁→13桁 変換

これらには JUnit のユニットテストを必ず付け、テストを仕様書として機能させる（MUST）。
少なくとも以下のケースを網羅する（MUST）。

- 棚番号が直前の巻から継承されること
- 巻単位で棚番号を変更した場合、それ以降の巻に新しい番号が継承されること
- 作品単位の一括更新が、他店舗の記録に影響しないこと

棚番号は「店舗 × 作品 × 巻」の組で一意に定まる。A店での棚番号変更がB店の記録に影響しては
ならず、この制約はスキーマ設計で表現する（MUST）。

**根拠**: 棚番号の継承は本アプリ固有かつ最も誤りやすいロジックであり、UI や DB に埋め込むと
検証も修正も困難になる。純粋 Kotlin に隔離することで、エミュレータも実機も不要な高速な
テストで仕様を固定できる。

### IV. 実機検証が必要な領域を明示する

以下はエミュレータで検証できない（MUST NOT: 自動テストの成功のみを完了根拠としない）。

- カメラによるバーコード読み取り
- 暗所（個室内）での動作
- 位置情報による店舗判定

これらに関わる実装を完了として報告する際は、「**実機での確認が必要**」と明示する（MUST）。
未確定事項（要求定義書「9. 未確定事項」＝棚番号シールがバーコードを覆う頻度）の解消も
実店舗確認に依存することを、報告時に併記する（MUST）。

**根拠**: 読み取り精度は本アプリの体験を左右するが、自動テストでは検出できない。完了の定義を
曖昧にすると、動かないものが「完了」として積み上がる。

### V. サーバを持たない

バックエンドサーバは構築しない（MUST NOT）。

- データはすべて端末内に保持する（MUST）。
- 新刊情報は外部 API から取得してよいが、自前の配信サーバは用意しない（MUST NOT）。
- 通知は WorkManager による定期取得とローカル通知で実現する（MUST）。
- 配架情報のユーザー間共有は行わない（MUST NOT / 要求定義書「8. スコープ外」）。

**根拠**: 個人利用が前提であり、運用コストと個人データの外部保管リスクを負う理由がない。

### VI. 入力操作を最小手数に保つ

記録は漫画喫茶の個室で、本を手に持った状態・片手で行われる。入力ステップを増やす変更を
加える際は、その必要性を説明しなければならない（MUST）。

- バーコード読み取りと ISBN 手入力は**同格の入力手段**として扱う。手入力を例外処理として
  扱ってはならない（MUST NOT）。両者は1操作で相互に切り替えられること（MUST）。
- 棚番号は直前の巻から自動継承し、未入力のままでも保存できること（MUST）。

**根拠**: 要求定義書「3.1 入力が発生する場面」のとおり、作品の識別・読書状態・棚番号の入力は
一連の操作として完結する必要がある。手数の増加はそのまま記録されないデータを生む。

### VII. やりとりは日本語で行う

- コード内の識別子は英語とする（MUST）。
- コメント、コミットメッセージ、仕様書、説明、レビューでの応答は日本語とする（MUST）。

**根拠**: 開発者・利用者ともに日本語話者であり、要求定義書も日本語で書かれている。用語
（読了・中断・離脱・棚番号）の訳揺れは仕様の誤解に直結する。

## 追加制約（プロダクト・データ）

- **対象プラットフォーム**: Android ネイティブ専用。iOS 対応およびマルチプラットフォーム化は
  行わない（MUST NOT）。
- **データ主権**: 端末内ローカル保持（原則V）。エクスポートは要求 F-4 として将来対応する。
- **棚番号の一意性**: 「店舗 × 作品 × 巻」で一意（原則III）。店舗をまたぐ更新は禁止。
- **作品の識別**: ISBN（バーコード上段13桁）を基本とする。10桁 ISBN の変換、および暫定名での
  記録と後からの正式作品への紐づけを扱えること。タイトルのあいまい検索は設けない
  （MUST NOT / 要求定義書「4.3」「8.」）。
- **将来拡張への配慮**: 今回スコープ外の要求（A-9、B-4〜B-6、C群〜F群）を後から無理なく
  追加できるデータ構造とする（MUST）。ただし、そのための実装を先行して行ってはならない
  （MUST NOT / 原則I）。
- **技術選定**: 具体的なライブラリ・データソースの決定は `/speckit-plan` フェーズで行う。
  外部書誌データソースの採用は、選択肢と根拠を提示し**承認を得てから**確定する（MUST）。

## 開発ワークフローと品質ゲート

- **仕様駆動開発**: `/speckit-constitution` → `/speckit-specify` → `/speckit-clarify` →
  `/speckit-plan` → `/speckit-tasks` → `/speckit-analyze` → `/speckit-implement` の順に実行する。
- **フェーズ停止**: 各フェーズの成果物が生成された時点で**必ず停止し、承認を求める**（MUST）。
  承認前に次フェーズへ進んではならない（MUST NOT）。
- **タスク順序**: ドメインロジックとそのユニットテストを、UI やカメラ連携より先に配置する
  （MUST / 原則III）。
- **ビルドゲート**: 各タスク完了時に `./gradlew assembleDebug` が通ることを確認する（MUST）。
- **完了報告**: 実機でしか検証できない項目は「実機確認が必要」と明示する（MUST / 原則IV）。
- **判断の帰属**: 人間が判断すべき事項をエージェントが推測で決めてはならない（MUST NOT）。
  迷う点は `[NEEDS CLARIFICATION]` として残し、`/speckit-clarify` で解消する。

## Governance

- 本憲法は、他のあらゆる開発上の慣行に優先する。ただし `docs/requirements.md` の要求内容に
  ついては原則Iのとおり要求定義書を正とし、本憲法はその扱い方を定める。
- **改訂手続き**: 改訂は、(1) 変更理由の記述、(2) 承認、(3) 依存テンプレート・ドキュメントへの
  波及確認、の3点を満たした場合にのみ行う。改訂時は本ファイル冒頭の Sync Impact Report を
  更新する。
- **バージョニング方針**: セマンティックバージョニングに従う。
  - MAJOR: 後方非互換な原則の削除・再定義
  - MINOR: 原則やセクションの追加、指針の実質的拡張
  - PATCH: 文言の明確化、誤字修正、意味を変えない調整
- **コンプライアンスレビュー**: 仕様・計画・タスク・実装の各成果物は、`/speckit-analyze` に
  おいて本憲法との整合性を確認する。特に原則II（購入・所蔵概念の混入）、原則III（棚番号の
  店舗独立性とテスト網羅）、スコープ外機能の混入を重点的に検査する。
- **逸脱の扱い**: 原則に反する実装が必要と判断した場合は、実装前に理由と代替案を提示し、
  承認を得る。承認された逸脱は plan の Complexity Tracking に記録する。
